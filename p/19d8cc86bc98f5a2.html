클로드 코드 제작자 Boris Cherny가 직접 쓰는 활용법 7가지

66추천도 실용성 20/25 · 신규성 7/15 · 최신성 4/10 · momentum 7/10
깊이 9/15 · 지속가치 10/15 · 신뢰도 9/10

핵심 포인트

역발상 3가지 (Boris가 핵심으로 꼽은 것)
  • 비용 아끼려 저렴한 모델을 쓰면 역효과. 저지능 모델은 수정·개입을 늘려 결국 토큰을 더 태운다. 최상위 모델(당시 Opus 4.6 + Max effort)이 같은 작업을 더 빠르고 정확히 처리해 오히려 싸다는 게 메이커 본인의 결론.
  • 작업을 1단계·2단계로 쪼개 강제하지 말 것. 목표와 필요한 도구만 주고 순서·맥락은 모델이 스스로 잡게 두면 결과가 더 좋다. 과잉 통제가 품질을 깎는다는 관점.
  • 작업의 약 80%는 Plan mode(터미널 shift+tab 두 번)로 시작. 계획을 먼저 검토·확정하면 그다음 실행에서 거의 한 번에 맞는 코드가 나온다.
일하는 방식 (실천 팁)
  • 병렬 세션이 기본값. Boris는 상시 5개 이상 에이전트를 동시에 돌리고, 각 세션이 20~30분 자율로 도는 동안 다른 일을 한다(커피 마시러 가는 식).
  • 터미널만 고집할 필요 없음. 데스크톱·모바일·Slack 연동 등 자기에게 맞는 인터페이스를 실험. 비개발 직군에는 데스크톱 앱이 진입이 쉽다.
  • Slack 채널·버그 리포트 스레드를 직접 읽게 연결하면 원인 분석·수정 제안·PR 작성까지 자동화. 메모리 누수 같은 문제도 모델이 자체 분석 도구를 만들어 원인을 찾는다.
  • Co-work로 이메일 요약·Slack 발송·스프레드시트 관리 같은 비코딩 업무까지 한 프롬프트로 위임. 여러 도구가 얽힌 복합 지시도 처리한다.
루프 4단계 (Claude Code 팀의 정의)
  • 턴 기반(매 프롬프트 트리거) → 목표 기반(/goal, 완료조건 명시·평가모델이 기준 충족까지 반복) → 시간 기반(/loop·/schedule, 주기 재실행) → 능동적 루프(스케줄+목표+동적 워크플로우 결합, 버그 triage 같은 대규모 반복). '프롬프트 대신 루프를 설계하라'는 흐름의 뼈대.
  • 품질 유지엔 코드베이스 정돈, SKILL.md로 자체검증 체계화, 별도 에이전트의 코드리뷰가 권장. 무조건 복잡한 루프보다 작업 성격에 맞는 primitive 선택이 먼저라는 점이 실무적이다.
  • 세션 성능 저하의 원인은 컨텍스트 창 오염(세션 기록·파일 내용·명령 출력 누적). CLAUDE.md 규칙, 자동 메모리, /compact, /clear로 능동 관리하라는 처방이 함께 붙는다.
읽는 각도 (지속성 vs 유효기간)
  • 버전 종속 정보(Opus 4.6, Max effort 기본값 언급)는 이미 낡았다. 반면 '플랜 먼저, 자율성 부여, 병렬화, 컨텍스트 관리'라는 원칙은 버전과 무관하게 유효해 이 글의 가치가 남는 지점.
  • 정리한 작성자는 순정 사용파로, 파일당 1000라인 제한·docs 참조·프로젝트별 '하지 마라' 문서 같은 가벼운 자기 규칙만으로 충분하다는 반례를 덧붙인다. 하네스 과설계가 필수는 아니라는 균형추.
