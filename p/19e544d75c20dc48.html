핵심 포인트

레포 5개, 각각 다른 용도
  • Zie619/n8n-workflows (Star 54,630): n8n 공식 사이트의 워크플로 전부 + 저자가 따로 수집한 것까지 한 레포에 밀어넣은 최대 규모 덤프. 양은 압도적이지만 분류가 얕아 탐색 비용이 큼.
  • enescingoz/awesome-n8n-templates (Star 22,381): 280여 개를 폴더별로 정리. 목적이 뚜렷할 때 가장 빨리 찾히는 쪽.
  • restyler/awesome-n8n (Star 2,882): 워크플로가 아니라 커뮤니티 노드 5,834개를 다운로드 순으로 정리한 인덱스. WhatsApp 자동화, PDF 생성, Firecrawl 스크래퍼 같은 통합이 이미 있는지 확인하는 용도.
  • lucaswalter/n8n-ai-automations: AI 에이전트 워크플로만 골라낸 선별본. LLM 노드가 들어가는 구성만 볼 때 노이즈가 적음.
  • Danitilahun/n8n-workflow-templates: 2,053개를 검색 가능한 형태로 정리. 키워드로 훑는 진입점.
어떻게 골라 쓸까
  • '워크플로 찾기'와 '노드(통합) 찾기'는 다른 문제다. restyler만 후자를 담당하므로 나머지 4개와 용도가 겹치지 않는다. 새 자동화를 설계하기 전 '이 서비스 노드가 존재하나?'는 여기서 먼저 확인하는 게 순서.
  • Star 수 순서로 접근하는 건 함정. 54k 레포는 사실상 덤프라 원하는 걸 찾는 데 시간이 더 든다. 목적이 분명하면 폴더 분류(enescingoz)나 검색(Danitilahun)부터 열고, 그래도 없을 때 최대 규모로 내려가는 순서가 낫다.
  • 템플릿은 그대로 임포트할 대상이 아니라 노드 구성 참고용으로 보는 편이 안전하다. 크리덴셜 매핑, 에러 핸들링, per-item 실행 모델(배열이 아이템 단위로 흐르는 부분)은 어차피 직접 손봐야 하고, 여기서 조용히 깨지는 경우가 대부분이다.
같은 피드에서 같이 걸린 것 (부록)
  • LangChain OpenWiki: GitHub 저장소를 읽어 위키를 만들고 매일 변경분만 자동 갱신. 프로그램은 MIT 무료지만 문서를 쓰는 모델 사용료는 각자 API 키로 부담.
  • kenn-io/agentsview: Claude Code·Codex·Cursor·Gemini CLI·OpenCode 세션을 자동 수집해 대화 검색, 토큰·비용 통계, 변경 파일 추적을 로컬 웹 UI와 CLI로 제공. 기본은 SQLite FTS5 전문 검색이고, OpenAI 호환 임베딩을 붙이면 의미 검색과 하이브리드 검색까지.
