핵심 포인트

context engineering 1년의 결론
  • CLAUDE.md처럼 세션 시작에 주입하는 마크다운 한 장이 비합리적으로 잘 먹혔다. 다만 그 파일이 길어지는 순간 context bloat로 바로 무너진다는 한계가 같이 드러났다.
  • memory tool 단계의 교훈은 자율성이다. 언제 읽고 언제 쓸지를 에이전트가 세션 안에서(in-band) 스스로 정하게 두는 쪽이 사람이 시점을 정해주는 것보다 잘 작동했다.
  • skill은 progressive disclosure로 bloat 문제를 푼다. front matter 몇 줄만 먼저 스캔하고 필요할 때 본문을 로드하니, 상세도와 context 절약을 동시에 얻는다. 단 무엇을 skill로 만들지는 여전히 사람이 정하는 병목이 남는다.
  • 지금의 state of the art는 메모리를 그냥 파일시스템으로 모델링하는 것. 전용 read/write 툴을 설계하지 말고 bash와 grep으로 검색하게 두는 편이 낫다. 에이전트는 이미 파일시스템 도구를 잘 쓴다.
이론이 프로덕션에서 깨지는 지점
  • 에이전트 여러 개가 같은 메모리 파일에 동시에 쓴다. 단일 에이전트 데모에서는 존재하지 않던 문제다.
  • 에이전트 하나가 조직 전역 context를 잘못 갱신하면 그 오류가 그걸 읽는 fleet 전체로 즉시 번진다. 블라스트 반경이 메모리 계층에 비례한다.
  • 메모리는 낡는다. 과거에는 맞았지만 지금은 틀린 항목, 애초에 잘못 쓰인 항목, prompt injection으로 심어진 항목까지 상정해야 한다.
메모리 시스템 가드레일 4가지
  • versioning: 롤백 가능하게 버전을 남기되, 값만이 아니라 어떤 세션·transcript를 근거로 바뀌었는지와 누가(사람인지 어떤 에이전트인지) 바꿨는지를 같이 기록한다.
  • concurrency: 쓰기 직전과 직후 해시를 떠서 불일치하면 커밋을 거부하고, 메모리를 다시 읽어 수정안을 새로 작성하게 한다. 사실상 optimistic locking을 에이전트 루프에 넣은 형태.
  • permissioning: 조직 전역 지식은 read-only, 에이전트 개인 스크래치패드는 write 허용처럼 계층별로 권한을 나눈다. 자율성을 주되 쓸 수 있는 범위를 계층으로 제한하는 게 핵심.
  • portability: 공들여 큐레이션한 메모리는 결국 여러 제품 표면에서 재사용된다. 처음부터 깔끔한 API로 이식 가능하게 설계할 것.
dreaming: out-of-band 메모리 큐레이션
  • in-band 메모리의 한계는 두 가지다. 첫째, 지금 시킨 과제와 미래의 자신을 위한 메모리 정리 사이에서 자원이 쪼개지는 최적화 문제가 생긴다. 둘째, 세션 하나의 시야밖에 없어서 세션을 가로지르는 반복 실패 패턴을 구조적으로 볼 수 없다.
  • dreaming은 배치로 비동기 실행되는 2차 프로세스다. 별도 토큰 예산을 받아, 메모리 스토어와 일정 기간의 세션 transcript를 함께 읽고 패턴을 찾아 메모리 변경안을 낸다.
  • 구현 형태: orchestrator가 sub-agent fleet에 transcript 분석을 뿌리고, 돌아온 결과 중 충분히 반복되는 패턴만 변경으로 승격한다. 각 제안에는 근거 transcript 예시와 그 문제가 얼마나 자주 났는지 통계가 붙어서, 사람이 수락·거부를 판단할 수 있다.
  • transcript는 사람과 에이전트의 대화 turn만 보는 게 아니라 tool call과 메타데이터까지 훑는다. 툴 설정이 잘못돼 계속 실패하는 종류의 문제는 대화만 봐서는 안 보인다.
  • 비유가 설계를 그대로 설명한다. 학생(에이전트), 채점하는 교사, 전체를 훑는 교장. 답안 전체를 보는 사람이 있어야 커리큘럼(공용 메모리)에 통째로 빠진 주제가 보이고, 전원이 똑같이 틀리는 방식(라디안 대 도)에서 툴 설정 문제를 잡아낼 수 있다.
효과와 비용
  • 같은 과제를 두 번째 할 때 정확도가 올라가고, one-shot 비율이 오르면서 토큰·지연·비용이 같이 내려간다. dreaming에 별도 예산을 태우는 비용은 여기서 상쇄된다는 게 발표의 주장.
  • 코딩 전용 기법이 아니다. 발표자 본인은 슬라이드·문서 작성 취향을 메모리로 축적해 쓰고 있고, 조직 전역 규칙(예: 특정 문장부호를 쓰지 말 것)도 같은 경로로 반영된다.
  • 출발점은 여전히 단순한 것이다. 마크다운 한 장과 skill, 그리고 에이전트에게 메모리 관리 자율성을 주는 것만으로도 멀리 간다. 가드레일과 dreaming은 에이전트 수가 많아지거나, 실행이 길어지거나, 도메인이 복잡해질 때 얹는 층이다.
Q&A에서 나온 것
  • "버전·동시성·내구성을 다시 만들면 결국 DB를 재발명하는 것 아니냐"는 질문에, 어떤 primitive가 잘 되는지 신호가 쌓였으니 그 부분은 harness에 결정적으로 박는 게 맞다고 답했다. 실제 설계 문제는 자율에 맡길 영역과 결정적으로 처리할 영역의 경계를 어디에 긋느냐다.
  • 권한이 제각각인 엔터프라이즈에서 dreaming이 권한을 어떻게 지키느냐는 질문에는, dreaming job에 붙일 transcript 집합 자체를 권한별로 골라서 메모리 스토어의 권한 범위와 일치시키는 방식으로 푼다고 답했다.
