핵심 포인트

핵심 전환: 계획을 컨텍스트가 아니라 이슈 트래커에 둔다
  • grill-me로 알려진 Matt Pocock의 새 스킬. 문제 정의가 명확하다. '한 에이전트 세션에 안 담기는 크기'의 작업을 어떻게 계획하느냐.
  • 해법은 plan.md 한 장을 키우는 게 아니라, 계획 자체를 repo 이슈 트래커의 map 이슈 하나 + 그 자식 티켓들로 쪼개 두는 것. 세션이 죽어도 지도는 트래커에 남는다.
  • map 본문은 index이지 저장소가 아니다. 결정은 각 티켓 안에만 살고, 지도는 한 줄 요약과 링크만 갖는다. 세션당 지도 본문 1회 로드로 저해상도 전체 상황을 잡는 구조라 컨텍스트 예산이 작업 크기에 비례해 늘지 않는다.
  • 티켓 본문은 '결정할 질문' 하나이고, 크기 기준이 명시돼 있다. 100K 토큰 세션 하나에 들어갈 것.
가장 훔칠 만한 규칙: Plan, don't do
  • 티켓은 빌드 슬라이스가 아니라 decision ticket이다. '무엇을 만들지 결정'만 다루고, 만드는 건 지도 밖으로 밀어낸다.
  • 이걸 판별하는 문장이 좋다. '그냥 해버리고 싶은 충동'이 들면 그건 지도의 가장자리에 도달했다는 신호이고 핸드오프할 때다. 스펙 문서가 슬금슬금 구현 지시서로 변질되는 흔한 실패를 규칙 한 줄로 잡는다.
  • 예외는 Notes에 명시적으로 적어야 한다. 실제로 PR 머지가 목적지인 지도에서는 '이 노력은 실행까지 지도 안으로 가져간다'를 Notes에 박아두고 task 티켓이 PR 수정을 직접 수행했다.
  • 세션당 티켓 1개 해결 상한(research만 예외). 에이전트가 한 세션에서 지도를 통째로 밀어버리는 걸 구조적으로 막는다.
티켓 4종과 HITL/AFK 경계
  • research(AFK), prototype(HITL), grilling(HITL, 기본값), task(둘 다). 여기서 진짜 핵심은 종류가 아니라 HITL/AFK 라벨이다.
  • HITL 티켓은 사람이 직접 답해야만 해소된다고 못 박고, '자기 질문에 자기가 답하는 grilling 에이전트는 이 규칙을 깬 것'이라고 실패 사례를 직접 지목한다. 에이전트가 사용자 의도를 상상해서 채워 넣는 문제를 프로세스 레벨에서 차단.
  • claim 규칙도 실무적이다. 작업 시작 전에 티켓을 assignee로 먼저 잡아야 하고, 미할당 열린 티켓 = 미점유. 여러 세션을 병렬로 돌릴 걸 전제한 설계.
  • blocking은 트래커의 네이티브 의존 관계를 쓴다. 이유가 명확하다. 트래커 UI가 frontier를 시각적으로 그려주므로 사람이 지도를 열지 않고도 지금 집을 수 있는 티켓을 본다.
fog of war: 계획을 일부러 미완성으로 둔다
  • 안 보이는 건 티켓으로 만들지 않고 'Not yet specified' 섹션에 흐릿하게 적어둔다. 티켓이 닫히면 그 앞의 안개가 걷히고, 그때 비로소 새 티켓으로 승격.
  • 판별 기준이 명쾌하다. '지금 답할 수 있느냐'가 아니라 '지금 질문을 정확히 쓸 수 있느냐'. 막혀 있어도 질문이 날카로우면 티켓, 아직 문장이 안 나오면 안개.
  • out of scope는 안개와 별도 섹션으로 분리하고 절대 승격되지 않는다. 목적지 밖으로 판명된 기존 티켓은 '해결'하지 말고 닫은 뒤 한 줄만 남기라고 한다. 이렇게 해야 Decisions so far가 실제로 걸어온 경로만 담는다.
  • 전체 계획을 미리 다 쪼개려는 습관에 대한 정면 반박이라 스킬을 안 쓰더라도 가져갈 만한 멘탈 모델이다.
실제 사용 흔적이 공개돼 있다는 게 이 글의 진짜 가치
  • 메일에도 '유튜브 실제 사용 사례 꼭 참고'라고 적혀 있었는데, 더 나은 자료는 Matt Pocock 본인 repo의 이슈 보드다. 스킬 문서가 아니라 실제로 돌아간 결과물을 볼 수 있다.
  • 현재 그 repo의 집계: map 6개, 하위 티켓 61개(grilling 37, task 13, research 9, prototype 2). grilling이 61%로 압도적이다.
  • 이 분포가 시사하는 바가 크다. wayfinder는 에이전트가 알아서 조사하는 도구가 아니라 사람과의 대화를 티켓으로 강제 분할하는 도구에 가깝다. AFK로 자동화되는 건 research 9건뿐.
  • 티켓 제목들이 그대로 좋은 예시다. 'Durable Pending + retry vs auto-discard: which failure handling stands?'처럼 하나의 선택지 대결로 떨어져 있다. 결정 티켓 쓰는 법을 여기서 그대로 베낄 수 있다.
  • 지도 하나가 도는 데 걸린 실제 시간도 확인된다. TikTok creator 지도는 2026-07-13 생성, 07-15 종료로 이틀.
적용 판단
  • 설치는 Claude Code 공식 마켓플레이스(`/plugin install mattpocock-skills`) 또는 `npx skills@latest add mattpocock/skills`. 전자는 읽기 전용 구독, 후자는 파일을 내 repo로 복사해 고쳐 쓰는 방식이고, 둘 다 깔면 스킬이 중복된다.
  • repo마다 `/setup-matt-pocock-skills`를 한 번 돌려 트래커(GitHub/Linear/로컬 파일)를 지정해야 한다. 지도와 티켓의 물리적 표현이 트래커별로 갈리기 때문.
  • 쓸 값어치가 있는 조건은 명확하다. 안개가 걷히지 않을 만큼 크고, 결정 사항이 며칠에 걸쳐 여러 세션으로 흩어지는 작업. 스킬 자체도 '차팅했는데 안개가 없으면 지도는 필요 없다, 멈추고 물어보라'고 적어놨다.
  • 반대로 한 세션에 끝나는 작업에 붙이면 이슈 트래커 오염만 남는다. GSD/BMAD 계열이 프로세스를 통째로 소유해서 중간에 손대기 어려운 문제를 피하려고 만든 스킬이라는 저자 설명과도 일관된다.
